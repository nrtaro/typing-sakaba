## 手元で確かめる

必要なもの：Node.js 24.15.0以降の24系、または26以降、npm（テストで `node:sqlite` とjsdomを使います）。

```powershell
npm ci
if (-not (Test-Path -LiteralPath .dev.vars)) { Copy-Item .dev.vars.example .dev.vars }
```

`.dev.vars` の `RANKING_IP_SALT` をランダムな長い値に変えてください。これはIPを保存用のハッシュにするための秘密値で、公開リポジトリには入れません。すでに `.dev.vars` がある場合は上書きせず、この項目だけ追加します。

```powershell
npm run build
npm run db:local
npm run dev:worker
```

`http://localhost:8787/` でビルドしたゲームとAPIが動きます。ここで使うD1は **このパソコンの `.wrangler/` 内だけ** です。仮のdatabase_idのままでも手元では確かめられます。

画面を直しながら確かめる場合は、別のターミナルで `npm run dev` を実行し、`http://localhost:5280/?slot=ranking-check` を開きます。`/api` は8787のWorkerへ転送します。Workerを止めているとランキングはエラー表示になりますが、通常営業とひがわり営業は遊べます。

確認の流れ：

1. 「はじめる」→「ひがわり」→難易度→今日のお題で、上位5人が表示されることを確認。
2. 営業を終え、Enterまたは `namae` で「なまえをいれる」を選ぶ。
3. 日本語で名前を入力。変換の確定Enterでは送られず、その次のEnterで送信されることを確認。
4. Escまたは「やめる」で閉じた場合は送られないことを確認。
5. 送信後に「今日○位／○人中」を確認。同じ端末の低い記録では、以前のベストが順位に使われる。
6. Workerを止め、上位の取得・送信に失敗しても遊べて、端末の記録が残ることを確認。

確認用の保存枠を片付ける場合は、ブラウザの開発者ツールで末尾 `.ranking-check` の `lastorder2.*` キーだけを消してください。普段の保存枠は消さないでください。

## 本番の準備（了承後）

1. 本番D1の `database_id` は `wrangler.jsonc` に設定済み。
2. 本番のテーブル作成は、ユーザーの了承を得てから次を実行。

   ```powershell
   npx wrangler d1 migrations apply typing-sakaba --remote
   ```

3. 本番用の十分長いランダムな秘密値を、次のコマンドで登録。値をチャットやコミットへ書く必要はありません。

   ```powershell
   npx wrangler secret put RANKING_IP_SALT
   ```

4. ゲームの確認後、ユーザーから反映の依頼があった場合にのみmainへマージ・push。

秘密値が未設定の場合、送信APIは503を返します。D1が未設定・利用できない場合もランキングだけエラー表示になり、静的ファイルは従来どおり配信します。

## 決めた細部

- 日付×難易度×端末IDで1つのベストを保存。上回ったときだけ、名前と成績を一緒に更新します。同点の名前変更はしません。
- 同点は同順位（1位・1位・3位）。同点内は、その点数を先に保存した人を先に表示し、さらに同じ時刻なら端末IDで順序を固定します。
- 名前は文字幅と前後の空白を整え、1〜10コードポイントで確認。制御文字・表示を紛らわしくする文字・簡単な禁止語を拒否します。名前はキャンバス上の文字として描き、HTMLとして扱いません。
- JSTの今日の記録を受け付けます。0時から5分未満は前日も受け付けます。開店時の日付で最後まで遊ぶ既存の動きは維持します。長い一時停止のあとなど、期限を過ぎた記録は端末にだけ残ります。
- 1つのIPまたは端末から直近10分に10回まで。低い記録や同点の送信も数えます。不正な入力は保存しません。送信履歴と保存をD1の1トランザクションにまとめ、同時送信でも制限を守ります。
- IPは秘密値を使うHMAC-SHA-256で保存。生のIPをDBに残しません。送信回数用の履歴は10分経過後、次の送信時に消します。ベストのIPハッシュは成績と一緒に保持します。
- 成績は売上上限（やさしい6万／ふつう10万／むずかしい12万円）、150皿以下、最大コンボが皿数以下、怒って帰った客300人以下、正確さ0〜1、打鍵/秒0〜15で確認します。料理を出しているのにコンボや正しい打鍵が0の記録も拒否します。売上は、報告された最大コンボによる倍率と、その日のお題の「ひでんの」「宴会」の回数からも上限を確認します。これは明らかに不自然な送信を止めるための確認です。改ざんを完全に防ぐ再現確認・Turnstileは段階6です。
- 通信は8秒で打ち切り、送れなかった記録は結果画面から再送できます。通信後に別の画面へ移っていたら、その返答で次の営業を変更しません。
- 同じ端末IDを含むGETの応答はキャッシュせず、APIには端末ID・IPハッシュを出しません。
- 上位と自分の順位はSQLで計算し、実SQLiteを通すテストで確認します。別の純粋関数へ同じ順位計算を重複実装しません。

## コードとテスト

- `worker/validation.ts`：保存や通信から独立した入力確認。`dailyConditions()` をゲームと共有。
- `worker/repository.ts`：同点の順位、ベスト更新、送信回数の制限。
- `worker/index.ts`：GET `/api/daily/top`、POST `/api/daily/score`、同一オリジン・本文サイズの確認。
- `migrations/0001_daily_ranking.sql`：スコアと送信履歴のテーブル。
- `src/ui/rankingClient.ts`：時間切れとエラーの処理。
- `src/ui/rankingName.ts`：日本語入力、Enter、Esc、フォーカスを扱うHTML入力。
- `src/core/save.ts`：保存枠ごとの端末ID、前回の名前。

```powershell
npm run typecheck
npm test -- --maxWorkers=1
npm run build
```

`tests/ranking*.test.ts` は入力・保存・実SQLiteでの順位と回数制限・API・通信失敗・名前入力を確認します。全体テストはボットによる難しさの確認を含み、1〜2分程度かかります。

2026-11-07の確認結果：全24ファイル・778テスト成功、型確認・ビルド成功。実際のローカルWorkerでは11件同時送信の10件を受け付け、1件を429で拒否しました。ブラウザでも日本語の名前の入力・Escでの取消・前回の名前の復元・送信後の「今日2位／2人中」、上位5人の表示を確認しました。実機IMEの変換動作と人による難しさの確認、本番環境での最終確認はこれからです。

順位計算はD1のSQLにまとめ、別の順位計算関数は作っていません。実SQLiteを使うテストが、その計算と自己ベストだけを使う動きを確認します。

Workerの静的配信ルートとトランザクションの仕様は、[Cloudflareの静的アセットのルーティング](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/)、[D1のbatch API](https://developers.cloudflare.com/d1/worker-api/d1-database/) に従っています。
