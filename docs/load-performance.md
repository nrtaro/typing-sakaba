## 変更

1. v3のロスレス画像を原本として残し、v4を配信用に生成。背景quality=88、人物・小物quality=94のWebP非可逆圧縮を採用。画像解像度を落とさず、透明度とコマ座標を維持した。
2. フォントの完了を待ってから画像を取得する直列処理を、並行取得に変更。フォント確定前はCanvasを隠し、文字が切り替わる様子を見せない。
3. 初期画面に不要なwife-fishing・wildlifeを、既存の4調達背景とともに遅延取得。背景・専用画像の両方を待ち、読込中に営業時計を進めない。
4. Performance APIへgame:boot、game:fonts-ready、game:images-ready、game:readyの計測マークを追加。game:readyは、画像・フォントが揃ったタイトルの最初の描画完了時点。

原本と最適化後を通常表示相当で並べた[画質比較](load-performance/image-comparison.png)、[最適化後のタイトル](load-performance-title.png)、[遅延画像を使った調達ヘルプ](load-performance/trip-help.png)を保存した。

黒・白への合成で、背景PSNRは31.84〜36.42dB、人物・小物は38.15〜44.75dB。全画像のアルファは完全一致する。RGBが完全一致する圧縮ではない。切り出し・足元・アニメーション情報は原本と等しいことをテストした。

## 計測条件と限界

- 同じWindows端末・アプリ内Chromiumブラウザー、1280×720。
- localhostの専用サーバーで、1ページ全体に共有10Mbpsの帯域上限と各レスポンス80msの待機を加えた。JS/CSS/HTMLはgzip、WebP/フォントはそのまま配信する。
- 各回で異なるURLパスを使い、Cache-Control: no-storeでブラウザーキャッシュを使用しない。変更前後それぞれ3回。
- 開始はページのナビゲーション時刻、終了はgame:ready。HTMLのloadイベントや画像のonloadだけを終了としない。
- 変更前はb638ef3の本番コードへ同じ計測マークだけを追加したビルド。比較用コピーは.load-benchmark/beforeに保持（Git管理対象外）。
- サーバー側で通信を制限したローカル比較であり、実際の携帯回線・CDN・低性能端末の速度を保証する結果ではない。CPU速度や実運用のキャッシュ方針でも変わる。
- 初期リソースは変更前131件・変更後129件。フォント全サブセットの先読みは維持した。フォント要求数の削減や画像の解像度削減は今回の対象外。

[生データ](load-performance-results.json)に各回のマーク、リソースごとの開始・終了時刻、本文・転送サイズ、画面サイズ、エラーを保存している。初期ロード6回と調達ヘルプの表示確認でブラウザーエラー・警告は確認されなかった。

## 再計測

1. 最適化前の本番ビルドを.load-benchmark/beforeへ保存し、最適化後をnpm run buildでdistへ出力する。
2. `node scripts/serve-load-benchmark.mjs .load-benchmark/before 5285` を起動する（localhostのみ）。
3. ブラウザーで `/before-1/`〜`/before-3/`、`/after-1/`〜`/after-3/` を順番に開く。
4. `#game`のdata-load-metrics属性を取得して保存する。属性は検証サーバーが追加する診断用スクリプトだけが生成し、本番ページには追加しない。

テストでは初期画像の除外、遅延画像が揃うまでの待機、重複取得の防止、失敗後の再試行、読込中の営業時計停止を確認する。

初回起動から営業・釣りへ進む操作確認も実施し、専用画像の初回取得後に正常描画されることを確認した。[初回の釣り画面](load-performance/first-fishing.png)。テスト632件・型チェックを含む本番ビルド成功。
